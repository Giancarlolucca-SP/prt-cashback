# S11-US04: API Backend e Contratos entre Modulos

## Epic
Arquitetura Tecnica, Banco de Dados e Base do MVP

## Objetivo
Definir os padroes de API backend, contratos entre modulos, validacoes, erros, filtros, paginacao, transacoes, eventos internos e integracao com jobs/adaptadores para manter o monolito modular organizado e seguro.

## Historia de Usuario
**Como** equipe de desenvolvimento,
**quero** padroes claros de API e contratos internos,
**para** implementar os modulos do MVP com consistencia, previsibilidade, seguranca, auditoria e facilidade de evolucao futura.

## Principios da API
- Backend API central e a fonte de verdade para regra de negocio e permissao.
- API deve validar autenticacao, RBAC, escopo e status do processo antes de executar acao.
- API deve ser modular por dominio, preservando separacao interna do monolito modular.
- Contratos devem ser previsiveis para o frontend.
- Eventos internos devem desacoplar acoes secundarias, como logs, notificacoes, jobs e integracoes.
- Integracoes externas devem passar por adaptadores, nunca espalhadas diretamente nos modulos de dominio.

## Organizacao de Endpoints
Padrao recomendado:

- Prefixo por dominio/modulo.
- Recursos no plural quando fizer sentido.
- Acoes sensiveis como comandos explicitos.
- Endpoints de listagem com filtros e paginacao.
- Endpoints de detalhes retornando apenas dados permitidos ao usuario.

Exemplos conceituais:

- `GET /customers`.
- `GET /customers/:id`.
- `POST /customers`.
- `PATCH /customers/:id`.
- `POST /sales/:id/approve`.
- `POST /sales/:id/generate-contract`.
- `POST /files/:id/delete-customer-document`.
- `POST /automation-rules/:id/test`.

## Padrao de Resposta
Respostas devem ser previsiveis:

- Sucesso com dados normalizados.
- Erros com codigo, mensagem, detalhe tecnico opcional e identificador de correlacao quando aplicavel.
- Listagens com `items`, `page`, `page_size`, `total` quando total for viavel.
- Dados sensiveis devem ser omitidos, mascarados ou bloqueados conforme permissao.

## Validacao de Entrada
Toda entrada deve validar:

- Tipos e formatos.
- Campos obrigatorios.
- Regras de negocio.
- Permissao do usuario.
- Escopo de acesso.
- Status/ciclo de vida do registro.
- Conflitos de concorrencia quando aplicavel.

## Erros Padronizados
A API deve diferenciar:

- `UNAUTHENTICATED`: usuario nao autenticado.
- `FORBIDDEN`: usuario autenticado sem permissao.
- `NOT_FOUND`: recurso inexistente ou oculto por permissao.
- `VALIDATION_ERROR`: dados invalidos.
- `CONFLICT`: conflito de estado ou concorrencia.
- `BUSINESS_RULE_ERROR`: regra de negocio impede acao.
- `EXTERNAL_SERVICE_ERROR`: falha em provedor externo.
- `JOB_ENQUEUED`: tarefa aceita para processamento assicrono.

## Paginacao, Filtros e Ordenacao
Listagens devem suportar, conforme necessidade:

- Paginacao.
- Busca textual simples.
- Filtros por status.
- Filtros por periodo.
- Filtros por responsavel.
- Filtros por modulo/etapa.
- Ordenacao por data, prioridade, status ou campo relevante.

Regras:

- Filtros sempre respeitam RBAC/escopo.
- Vendedor/SDR nao devem receber totais ou pistas de dados fora do escopo.
- Dados financeiros/margem/custos so aparecem para perfis autorizados.

## Transacoes
Operacoes que mudam multiplas entidades devem usar transacao quando necessario:

- Fechamento de venda.
- Geracao de contrato e snapshot.
- Lancamento financeiro vinculado a venda/veiculo.
- Ajuste de comissao.
- Mudanca de etapa com historico.
- Exclusao de documento de cliente com log.
- Transferencia de carteira/responsabilidades.

## Eventos Internos
Acoes importantes podem emitir eventos internos para desacoplar efeitos secundarios.

Exemplos:

- `customer.created`.
- `lead.stage_changed`.
- `sale.closed`.
- `document.uploaded`.
- `document.deleted`.
- `vehicle.price_changed`.
- `listing.sold`.
- `service_order.delayed`.
- `permission.changed`.
- `automation.triggered`.

Eventos podem gerar:

- Audit log.
- Notificacao.
- Job assicrono.
- Sincronizacao externa.
- Atualizacao de historico.
- Sugestao/alerta.

## Jobs e Processamento Assicrono
A API nao deve bloquear a resposta em tarefas demoradas.

Devem virar job:

- Envio WhatsApp/e-mail.
- OCR/leitura assistida.
- IA/sugestoes.
- Consultas externas.
- Sincronizacao de anuncios/marketplaces.
- Webhooks externos.
- Reprocessamento de falhas.
- Relatorios pesados quando aplicavel.

A resposta deve indicar:

- Job criado.
- Status inicial.
- Identificador para acompanhamento.
- Processo vinculado.

## Adaptadores de Integracao
Integracoes devem ser isoladas em adaptadores:

- Evolution API / WhatsApp.
- E-mail operacional.
- Supabase Storage.
- OCR/leitura assistida.
- IA.
- Marketplaces.
- Consultas externas autorizadas.
- Despachantes/prestadores quando houver canal.

Regra:

- Modulos de dominio chamam interfaces internas.
- Adaptador implementa o provedor real.
- Troca futura de provedor nao deve exigir reescrever regras de negocio.

## Contratos entre Modulos
No monolito modular, modulos devem conversar por servicos/contratos internos claros.

Exemplos:

- Vendas consulta cliente e veiculo por servicos internos, nao acessando diretamente regras privadas de outro modulo.
- Financeiro recebe eventos/snapshots de venda, veiculo e custos.
- Anuncios consome veiculo/estoque e publica por adaptador.
- Automacoes consomem regras, eventos e notificacoes.
- Auditoria recebe eventos de acoes sensiveis.

## Auditoria na API
Toda acao sensivel deve gerar audit log:

- Criacao/alteracao/inativacao de usuarios.
- Alteracao de permissao.
- Alteracao financeira.
- Ajuste de comissao.
- Exclusao de documento de cliente.
- Exportacao de dados.
- Acesso bloqueado a dados sensiveis.
- Reprocessamento tecnico relevante.
- Acao automatizada aprovada por humano.

## Evolucao Futura da API
- Se algum modulo for extraido para servico separado, seu contrato interno deve virar contrato HTTP/evento/fila.
- Eventos internos podem evoluir para mensageria externa se volume justificar.
- Relatorios pesados podem migrar para endpoints assicronos/materializacoes.
- Contratos devem ser versionados quando mudancas quebrarem compatibilidade.

## Decisoes a Confirmar
1. Confirmar padrao REST/JSON para API do MVP.
2. Confirmar que a API deve ocultar dados fora do escopo, sem revelar totais/pistas para perfis sem permissao.
3. Confirmar que tarefas demoradas devem sempre virar job assicrono.
4. Confirmar uso de eventos internos para logs, notificacoes, automacoes e sincronizacoes.
5. Confirmar que integracoes externas sempre passam por adaptadores.
6. Confirmar que acoes sensiveis devem ser transacionais e auditadas.

## Criterios de Aceite
- Dado que usuario chama endpoint protegido, quando backend validar, entao permissao e escopo devem ser aplicados antes da resposta.
- Dado que usuario sem permissao consulta recurso, quando solicitar, entao API deve bloquear ou ocultar conforme regra definida.
- Dado que listagem possui filtros, quando retornar dados, entao deve respeitar escopo do usuario.
- Dado que acao sensivel altera multiplas entidades, quando executar, entao deve usar transacao quando necessario.
- Dado que tarefa demorada e solicitada, quando aceitar, entao deve criar job e retornar status inicial.
- Dado que provedor externo muda, quando trocar adaptador, entao dominio nao deve precisar reescrever regra de negocio.
- Dado que acao sensivel ocorre, quando concluir, entao audit log deve ser criado.

## Fora de Escopo
- GraphQL no MVP, salvo decisao futura.
- API publica para terceiros externos no MVP.
- Microservicos no MVP.
- Versionamento publico complexo antes de existir consumidor externo.
- Mensageria externa obrigatoria no MVP.

## Evolucao Futura
- REST/JSON pode evoluir com OpenAPI/documentacao formal.
- Webhooks externos podem ser adicionados por modulo quando houver integracoes oficiais.
- Contratos internos podem virar contratos entre servicos se algum modulo for extraido.
- Paginacao e filtros podem ganhar indices/materializacoes conforme volume real.
